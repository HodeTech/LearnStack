# ADR-0102: Production Tenant Onboarding and Authority Rebind

## Status

Proposed — 2026-11-19, for the maintainer's review. It closes no gate, changes no
Accepted record and authorizes no code until Accepted. Acceptance would close the
production first-admin, provisioning, recovery and issuer-rebind parts of gate G13
together with [ADR-0101](0101-platform-operator-authority.md).

**Date:** 2026-11-19
**Deciders:** @cemil

## Decision Drivers

- [ADR-0072](0072-application-owned-identity-bootstrap.md) and
  [ADR-0073](0073-scoped-membership-and-identity-data-foundation.md) leave production
  first-admin setup and a controlled issuer rebind to P03-9. The fixed seed capability
  grants no operator authority, and no production rename path exists.
- `ProvisionTenantCommand` and the identity seed handlers accept only the `Seed` source.
  Nothing outside the Seeder, which refuses no deployment mode, creates a Tenant,
  its Role templates or a first administrator. Host-to-tenant mappings arrive in
  production only through a Hub endpoint that does not exist
  ([Phase 02c](../roadmap/phase-02c-hub-foundation.md)), so the no-Hub baseline cannot
  make a tenant reachable.
- The invariants that make an administrator safe, last-admin protection, the User fence
  and ordered membership locks
  ([ADR-0074](0074-membership-admission-under-ordered-locks.md)), live in app-role
  domain code. A raw write on the platform connection skips them and the audit capture
  of [ADR-0044](0044-audit-write-path.md) § 7.
- `identity_authority` is a singleton qualified once at startup. Subject keys hash its
  `AuthorityId` ([Database Standards](../standards/05-database.md)), so an issuer change
  that alters the id re-keys every person and can resurrect a closed tombstone.
- C14 asks for positive and denied proof, partial-commit proof, unknown-COMMIT
  reconciliation and identity continuity, and says seed authority is insufficient.

## Considered Options

1. **Operator-admitted acts on the app role through the ordinary pipeline, and an
   offline rebind that is still an admitted operator act** (chosen). Invariants, RLS and
   audit capture stay where they are proven.
2. **Run onboarding as raw SQL on the platform connection** (rejected). It skips the
   last-admin and User invariants and the audit capture, and widens a `BYPASSRLS` role.
3. **Accept the `Seed` source in production** (rejected). The Seeder is a development
   tool with fixed identities and no mode refusal.
4. **A platform-issued invitation for the first administrator** (rejected here). It
   reuses [ADR-0093](0093-verified-invitation-acceptance-and-handoff.md) but needs an
   exception for an inviter who holds no membership, and it adds an email dependency to
   recovery.
5. **A rebind through an HTTP operator act under a runtime admission freeze**
   (rejected). It puts a database read on every authentication and keeps old issuers
   alive in running processes, because the qualification is startup-only.

## Decision

1. **A confined operator source.** `AuthorizationSourceKind` gains `PlatformOperator`,
   minted only from an [ADR-0101](0101-platform-operator-authority.md) admission. The
   operator acts below accept that source and no other, and the `Seed` policies stay
   `Seed`-only, so neither authority can perform the other's acts. The target tenant is
   announced by that source through exactly one new confined setter call in the closed
   census, never from a request value, and the platform role is not used. Step 2 fixes
   the exact origin value against the code.
2. **The act family.** Four acts, each a `platform.*` permission under ADR-0101:
   provision a Tenant with its default Organization and map its hosts through the
   existing commands; create the finite Role templates; create the first tenant-wide
   administrator Membership; recover a tenant that has none. Tenancy provisioning keeps
   its Tenant and default Organization pair. The tenant id is generated by the server
   and never chosen by the operator; a retry carries an idempotency key.
3. **Naming the person.** The operator names the first administrator by provider subject
   at the identity authority's issuer. The person must already have completed new-user
   bootstrap, so a `users` binding exists. A confined single-act resolver maps the
   subject to a `UserId`; an unknown subject refuses with a bootstrap-required outcome.
   The operator creates no `User`, and an email address is never an identifier.
4. **Separate transactions, resumable.** Provisioning, each Role template and the
   Membership commit in their own transactions, as
   [ADR-0073](0073-scoped-membership-and-identity-data-foundation.md) requires. A retry
   after partial setup resumes from the first absent step by reading state, with the
   pristine-prefix predicates of the Role roots. An unknown COMMIT is reconciled by that
   read, never by a blind repeat. Naming a tenant that does not exist, or a person who
   is not bootstrapped, refuses before any write.
5. **Recovery.** Recovery uses the same acts and refuses unless, inside the transaction,
   the tenant has no active tenant-wide administrator. Its reason slug differs, and the
   last-admin invariant is unchanged. The act is not a tenant-administrator escalation
   path.
6. **Audit.** Each step writes its MUST row in its own transaction through the ordinary
   pipeline, under the real target tenant, with the operator attribution of
   [ADR-0101](0101-platform-operator-authority.md) § 9.
7. **Controlled issuer rebind.** The rebind changes only the origin of
   `identity_authority.issuer`, under the same realm path. It preserves `AuthorityId`,
   subject keys, actor ids and closed tombstones, and no realm rename is admitted.
   It is an offline operator act: a new verb of the authority installer tool runs while
   the API and worker fleets are stopped, accepts the human's operator access token,
   is admitted for `platform.identity_authority.admin`, enters the platform scope, and
   writes its MUST result row on that scope's work transaction.
8. **Frozen admission.** The tool refuses unless it holds a session-level exclusive lock
   and observes no other session of the application or outbox role. It does not trust an
   operator's statement that the fleet is stopped.
9. **Continuity proof.** Before the change, the tool reads the new issuer's discovery
   and key set, enumerates every user of the new realm through the realm Admin API with
   the deployment's own credential, and hashes each `sub` under the preserved
   `AuthorityId` exactly as the binding does. Every active stored subject key must be
   present. A closed tombstone key must be absent, so a closed person cannot reappear.
   Any miss, or an enumeration that does not complete, refuses.
10. **Database guard.** The platform role receives `UPDATE (issuer)` on
    `identity_authority` and nothing else on it. A trigger refuses any other column,
    refuses an issuer that breaks the realm grammar and refuses the change unless the
    transaction announced the rebind token the tool sets. Processes that start with the
    old issuer fail qualification, so a restart with the new configuration is the
    unfreeze.
11. **Seed capability.** The Seeder refuses to run when `Deployment:Mode` is not
    Development. A test proves the seed source cannot perform an operator act and the
    operator source cannot perform a seed act.

## Context

Onboarding is not the platform scope's job. The scope exists to cross tenants and write
platform tables, and the platform role bypasses row security. A first administrator is
the opposite case: one tenant, ordinary tables, and the strongest invariants in the
Identity module. Running it on the app role keeps those invariants and the capture of
[ADR-0044](0044-audit-write-path.md) § 7, and costs one new confined source and one new
setter call, which the closed census makes visible and testable. The cost is real: the
source enum, the setter census and the minting rules of the authorization candidate all
change, and the existing negative controls must keep refusing everything else.

Naming a person by provider subject keeps email out of authority. It asks the person to
sign in once first, which is the same zero-membership entry P03-3 already ships. The
operator reads the `sub` from the issuer's own console, which the operator already
holds.

The rebind is rare and dangerous, so it is shaped to be hard to do by accident. An HTTP
act would need a runtime freeze on every authentication and still could not retire the
issuer that running processes hold. Offline with a lock, a session check, a continuity
proof and a guarded column makes each claim checkable without touching the hot path.
What the session check cannot see is a process on another database role or another
cluster node that the deployment forgot; the runbook states it.

The host mapping is included because a tenant that resolves to no host is not onboarded.
It does not widen the Hub contract: the Hub endpoint stays the Hub's, and this act
reuses the existing mapping command.

What would reopen this: a Hub that pushes provisioning and mappings, a need for a
self-service first administrator, or a realm rename.

## Consequences

### Positive

- No production onboarding depends on the development seed, and a test proves the two
  authorities cannot substitute.
- The last-admin and User invariants and the audit capture are unchanged and exercised.
- The rebind is checkable: a continuity set, a lock, a guarded column and a result row.
- The no-Hub baseline can create a reachable tenant with an administrator.

### Negative

- A new authorization source kind, a new confined setter call and a new definer-style
  resolver widen closed sets that tests currently pin, so each census is edited
  deliberately.
- An operator needs the person's `sub` and the person must sign in first.
- A rebind needs a downtime window.

### Neutral

- `ProvisionTenantCommand` and the host command gain the operator source beside `Seed`.
- Seeded Development tenants are unaffected.

## Implementation Notes

- Step 2 delivers the source, setter call, resolver, acts, routes, rebind verb, guard
  migration and canonical SQL, the Seeder mode refusal, and the tenant onboarding and
  rebind runbook. The migration changes the grants table in
  [Database Standards](../standards/05-database.md) and the pinned grant expectations in
  the same commit.
- Proof: positive and denied acts; wrong tenant; unbootstrapped person; interruption
  between every pair of steps with a retry that completes once; an unknown COMMIT; the
  last-admin invariant after recovery; seed insufficiency in both directions; a rebind
  with a missing, extra and tombstoned subject, a live second session and an unchanged
  `AuthorityId`. The mutation targets are the source check, the in-transaction no-admin
  test, the continuity comparison and the guard trigger.
